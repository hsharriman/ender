1. Mislabelled transversal premises 6 DS filesproof file

What's wrong. In transversal(s1p1, s1p2, t1, i1, s2p1, s2p2, t2, i2):

  • i1 and i2 are the two crossing points.
  • t1 and t2 are the transversal's far ends past those crossings. When the transversal stops at a crossing, they equal the crossing.
  • s1p1→s1p2 must point the same way as s2p1→s2p2.

These files make two mistakes:

  • t1/t2 hold the other crossing point. For example, transversal(S,P,Q,P,…) has t1=Q, which says "Q lies beyond P, away from Q". No figure satisfies that.
  • Some reverse the second segment, so a point lands in a slot claiming the wrong side of the transversal.

Each fix below was derived from the quadrilateral's vertex order and run through this branch's checker. All six are accepted after the change:

2. sim_seg, the language 4 filesthe language

What's wrong. sim_seg(AB, DE) relates only two segments, so it can't express a shared scale factor. SSS similarity needs AB/DE = BC/EF = AC/DF, and two-segment statements can't carry that. The legacy checker gets away with it because sas_sim and sss_sim reuse checkSas/checkSss (reasonApplication.ts:436-450) and only check which sides correspond. The audited language has proportion(a,b,c,d) (SegmentProportion in rocq/Ender/Audit.v), but that statement isn't in the legacy catalog.

Fixtures: triangles/sas_sim_correct.txt, sss_sim_correct.txt, sas_sim_incorrect.txt, sss_sim_incorrect.txt.

Option A: add proportion to the legacy catalog and respell the fixtures

For example proportion(AB, DE, AC, DF). Files:

  • stmts.defs.ts: add proportion; drop sim_seg at line 117.
  • reasons.defs.ts: sss_sim and sas_sim dependencies (lines 304 and 311), and the csstp conclusion (line 648).
  • premises.ts: lines 67 and 246.
  • proofObjText.tsx:72
  • proofObjDiagramAdditions.ts: lines 66 and 188.
  • New sim checks in reasonApplication.ts.

Option B: add sim_seg to the audited language

Files: rocq/Ender/Syntax.v, Audit.v, and the parsers. You would still have to decide what a two-segment statement means.

3. Trailing step references on premise lines 6 filesproof file, or the grammar

What's wrong. Lines like [g_1] perp(LU, PS, S) [01] repeat the step number that [01] given(g_1) already gives. The legacy grammar tolerates the suffix; the audited header grammar doesn't parse it.

Files: examples/s2inc1corrected.txt, examples/s1inc3.txt, examples/s2inc1.txt, DS s1inc2.txt, DS s1inc3.txt, DS s2inc1.txt.

Options:

  • Strip the suffix (recommended, since it carries no information). This touches only those 6 files.
  • Admit the suffix in rocq/Ender/PresentationParser.v / PublicParser.v.
Extra fix for s2inc1corrected.txt. Even with the suffix stripped, step 9 is rejected. Step 7's a_SLP only equals the triangle's a_NLU if S lies on LU, and nothing places it there. Adding [d_3] on_line(LU, S) makes it accepted.

4. examples/buggypgram_opp_angs.txt 1 fileproof file

What's wrong. The file declares quad: q_ABCD and then gives parallelogram(q_BCAD). BCAD is not a rotation of ABCD, so it names a different, undeclared quadrilateral with sides BC, CA, AD, DB. Its opposite-angle pairs are at B/A and C/D, so the goal con_ang(a_BAD, a_BCD) doesn't follow from it. The legacy checker still accepts the file, which looks like a legacy soundness gap.

Options:

  • Change it to q_ABCD. It would then duplicate quadrilaterals/pgram_opp_angs_correct.txt.
  • Keep it as a regression test and change its marker to // fail on step 2.

Given the "buggy" name, the second was probably the intent.

5. DS holt_s2-7_cio3_c1.txt 1 filearguably the checker

What's wrong. This is the vertical angles proof. It has only intersect_seg(AC,BD,E) and seg: AC BD. The audited intersect_seg is endpoint-inclusive, so E could equal A, and then the angle's rays are degenerate. Its sibling DS holt_s2-7_ex3_c1.txt declares seg: AC BD AE EB CE ED and is accepted. Legacy accepts both.

Options:

  • Fix the file: add AE EB CE ED to seg:.
  • Change the checker: make IntersectSeg strict betweenness in rocq/Ender/Audit.v (with matching Checker.v changes), so the crossing can't be an endpoint.

6. Unused steps and duplicate conclusions 1 filepolicy

What's wrong. DS transversal_test.txt proves para(AB,CD) three ways, so steps 5 and 6 are unused duplicates.

  • Legacy rejects it. collectProofCheckerIssues in src/checker/proofChecker.ts:217-233 counts Unused steps and Duplicate steps as issues. Running it confirms it emits unused_step and duplicate_conclusion.
  • The verified checker reports both but still accepts.

If you confirm "non-fatal": nothing changes on the rocq side. Optionally, change the legacy proofChecker.ts to match.

Watch out: the solver relies on unused givens being flagged, so solver output should keep covering all g_n premises. If you relax this in legacy, keep that behaviour for the solver.

7. DS s1c1_wp1.txt: six-argument transversal 1 fileproof file

What's wrong. It writes transversal(A, C, A, B, D, B) with only six arguments. The legacy checker also refuses it ("expects 8 points").

Fix: respell to transversal(A, C, A, A, D, B, B, B). After that, legacy rejects it at step 3, which is the step its own // corrupted comment marks. So the marker should also change from // pass to // fail on step 3.

9. Old or unknown vocabulary 4 filesproof file

circles/reg1.txt and reg1v2.txt

  • They use inscribed_tri, which exists in no catalog.
  • They use the old arc token con_arc(BR_OB, YD_OB). The rocq branch replaced it with minor_arc(c_OB, B, R); this branch has no such spelling yet.
  • Their titles are copy-pasted from con_inscribed_angs even though they prove RHL.
  • reg1v2 also has an empty step [05], which rhl cites.

Recommendation: delete both. Respelling would mean swapping inscribed_tri for radius(...) premises and converting the arcs.

DS holt_s11-4_exer32_c1.txt and DS holt_s11-6_cio6_c1.txt

  • They write inscribed_angle(a_ACB, AB) (angle, chord). The current form is inscribed_angle(c_OA, a_ACB) (stmts.defs.ts:192).
  • exer32 respells exactly like our examples/inscribed_angles.txt, plus a circ: c_OA line.
  • cio6 declares no circle or centre at all, so it needs a centre point added too.
  • Both also use con_inscribed_angs, so respelling alone won't get them accepted (see the last section).

11. radius_chord_bisect_conv 2 filesthe language

What's wrong. The theorem says "the perpendicular bisector of a chord passes through the centre". The corpus concludes radius(c_OR, T) instead, which claims T, the far end of segment OT, is on the circle. Sliding T further out along the line keeps every premise true, so the conclusion doesn't follow. The legacy check (circleChecks.ts:165-197) only verifies that T is an endpoint of the bisector. DS holt_s11-2_exer43_c1.txt passes only by naming coincidence: its circle is c_AJ and it concludes radius(c_AJ, J).

Fixtures: circles/radius_chord_bisect_conv_correct.txt, DS holt_s11-2_exer43_c1.txt, and the _incorrect twin.

Option A: new conclusion form

Something like "line s passes through the centre of c". Files:

  • stmts.defs.ts: the new statement.
  • reasons.defs.ts:550: the conclusion.
  • circleChecks.ts: the check.
  • proofObjText.tsx and proofObjDiagramAdditions.ts: text and diagram.
  • ERROR_CODES.md: the PT_NOT_ENDPOINT entry.
  • The fixtures.
  • On rocq: Syntax.v and Audit.v.

Option B: retire it

Remove:

  • the reason entry in reasons.defs.ts
  • the case at reasonApplication.ts:691
  • the check function
  • its error code in ERROR_CODES.md
  • both fixtures and the DS file

12. linear_pair_conv 1 filethe language

What's wrong. supplementary only relates angle measures. A linear pair also needs the outer rays to be opposite, which is a fact about the figure. The catalog text even says "if two adjacent angles…", but the only dependency is supplementary (reasons.defs.ts:209). The legacy check reuses linear_pair() at reasonApplication.ts:372. In lines_angles/linear_pair_conv_correct.txt, nothing says C lies between A and B.

Option A: add a diagram premise

Such as on_line(AB, C). But that premise alone makes the conclusion follow, so the supplementary dependency does no work.

Option B: retire it (recommended)

Remove:

  • the reason entry
  • the case in reasonApplication.ts
  • both fixtures
  • the reason from the solver's reason list if it's there

con_inscribed_angs and inscribed_angs the language

What's wrong. Two inscribed angles on the same chord AB are congruent if their vertices lie on the same arc, and supplementary if they lie on opposite arcs. inscribed_angle(c_OA, a_APB) doesn't say which arc P is on. The legacy check (circleChecks.ts:200-235) only verifies a shared chord and that the points are on the circle.

Files affected:

  • Fixtures: circles/con_inscribed_angs_correct.txt and _incorrect.txt, examples/inscribed_angles.txt, and the two DS files from item 9.
  • Definitions: stmts.defs.ts (inscribed_angle) and reasons.defs.ts (lines 557 and 692; the second already has a "should these even be implemented?" TODO).
  • Checker: circleChecks.ts.
  • On rocq: Audit.v.

Options:

  • Let inscribed_angle name the intercepted arc, e.g. a third minor_arc/major_arc argument.
  • Add a separate premise saying the two vertices are on the same side of the chord.

Either way, the rule would then conclude con_ang for same-arc vertices, and a supplementary version could be added for opposite arcs.

Proof-file-only fixes: items 1, 3 (stripping), 4 (marker), 7 and 8. Six of them are in the geo-proof-dataset submodule, so they would be committed there.
